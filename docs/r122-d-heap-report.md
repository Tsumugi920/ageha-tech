# R12.2-D 剩余 JS 堆增长归因与复验

日期：2026-11-02。调查对象为上一轮记录的约 **2.51MiB** 增长。使用已有生产构建、相同首页 → about → 首页流程、high 档与减少动态效果；每轮强制 GC 后读取 `Runtime.getHeapUsage`。

## 结论

原 12 轮增长的主要来源已定位：**V8 编译预热，以及 Three 数字 ID 索引缓存的底层存储容量变化**。本轮未观察到按原速率继续累积的场景、Mesh、几何、材质、贴图或 renderer 实例保留。

普通浏览器延长到 **48 轮**：堆在第 16 轮达到 **23.604MiB**，第 17 轮回落至 **22.020MiB**，第 48 轮为 **22.548MiB**。最后 12 轮范围 **22.331–22.548MiB**，跨度 **0.217MiB**；仍有约 **0.0162MiB/轮**的小幅后段斜率，不能表述成绝对零增长或无限时长无泄漏保证。

**没有修改业务源码、渲染器资源释放逻辑、全局 ID、第三方依赖或产品启动参数。** 本轮只扩充采集工具，增加分轮堆快照及明确标记的控制实验；既有 R12.1、A/B/C/D 成果及旧证据通过哈希复核。

## 一、复现与排除

| 实验 | 条件 | 第 1 → 12 轮 JS 堆 | 增量 | 浏览器检查 |
| --- | --- | --- | --- | --- |
| `baseline-pair` | 正常生产页面，第 1/12 轮抓快照 | 20.668 → 23.155MiB | 2.487MiB | 41/41 |
| `console-control` | 原始事件归档后清理浏览器控制台存储 | 20.689 → 23.274MiB | 2.585MiB | 41/41 |
| `jitless-control-02` | 独立 Chrome 使用 `--js-flags=--jitless` | 14.152 → 15.544MiB | 1.392MiB | 41/41 |

控制台存储清理没有消除增长，排除了其作为主要原因。清理操作只用于对照，逐次写入事件日志，先前 console/warn/异常仍完整保留在 `events.jsonl`；正常 48 轮未清理控制台。

关闭 JIT 后，增长减少约 **1.10MiB**；这与正常组新增机器码的量级一致。该启动标志仅用于归因，**不是产品配置或性能优化建议**，其数值不能作为正常运行的性能成绩。

首个 jitless 尝试因 CDP 尚未就绪而连接失败，保留原始失败记录；表内为成功重试 `jitless-control-02`，没有把启动失败记作应用错误或通过样本。

## 二、快照中的主要增长

`baseline-pair` 的第 1/12 轮快照通过稳定对象 ID 作差分，并追踪强引用链；没有仅凭总堆量判断泄漏。

| 项目 | 实测增量 | 证据 |
| --- | --- | --- |
| V8 `InstructionStream` | 1,115,840B，约 1.064MiB | `baseline-pair/heap-delta.json` |
| 全部 V8 `code` 类自身大小 | 1,661,664B，约 1.585MiB | `baseline-pair/binding-cache-analysis.json`；包含机器码、反馈及相关编译结构 |
| Three 绑定缓存三层底层存储合计 | 884,384B，约 0.843MiB | 同文件中 program/object/geometry maps 的底层大小之和 |
| 上述代码与缓存两类合计 | 约 2.428MiB | 与总堆约 2.487MiB 的增长接近，其余为小型运行时/对象等条目变化 |

快照中的对象自身大小与 Runtime 堆总量口径不同，上表用于归因和量级核对，不把它们当作可精确相加的保留子树大小。

主要数组的引用链进入当前 renderer 的绑定状态缓存、几何索引表等；编译结构进入 Three 渲染相关函数的 V8 代码。未出现与往返次数相对应的一批旧场景资源实例。快照中也可见浏览器历史、资源与性能计时记录增加，它们是较小的附加项，不应把所有变化笼统称作业务泄漏。

原始保留链：`baseline-pair/growth-retainers.txt`、`elements-retainers.txt`；实例和缓存统计：`binding-cache-analysis.json`。

## 三、数字 ID 缓存的容量效应

已安装的 Three r186 在 `WebGLBindingStates` 中按 `geometry.id → object.id → program.id` 索引普通对象；program ID 随创建递增。几何及 shader 数量相近，并不意味着这些对象的底层存储字节数也相近。

正常 48 轮快照显示，**programMap 的对象数一直为 296**，但底层大小随数字键范围变化：

| 轮次 | 最大 program ID | programMap 对象数 | programMap 底层字节 |
| --- | --- | --- | --- |
| 1 | 121 | 296 | 186,412B |
| 12 | 792 | 296 | 1,353,108B |
| 24 | 1,524 | 296 | 24,624B |
| 48 | 2,988 | 296 | 24,624B |

第 24–48 轮的缓存容量已保持一致；数字 ID 继续增加，缓存对象数量没有增加。底层存储收缩也与第 17 轮附近的堆回落相符。

为排除只凭源码推测，另在独立空白页面建立 **256 个对象、每个只有一个数字键**，替换旧集合并 GC，复现同型结构的容量变化：

| 数字键 | 相对空集合的堆增量 |
| --- | --- |
| 100 | 181,548B |
| 500 | 795,948B |
| 900 | 1,410,348B |
| 1,500 | 26,980B |
| 5,000 | 26,980B |

对象数量与键数量没有增加，存储却先增大再收缩，与 V8 对稀疏数字键采用不同存储布局一致。原始数据及三个快照在 `cache-shape/`。因此本轮没有通过重置 Three 全局 ID、修改库代码或改动场景来压低测量值。
