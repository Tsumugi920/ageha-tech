# Ageha.tech 3D 世界优化方案

> 整理日期：2026-10-29。
> 状态：待实施的优化建议，不是已完成功能清单或性能验收报告。
> 目标：参考 Bruno Simon 网站的体验完成度，建设具有 Ageha 原创身份的可玩 3D 作品集，而不是复制场景、汽车、素材或代码。

## 1. 结论与优化方向

当前项目已经具备可用的 3D 探索骨架，但整体更接近“可以漫游的三维展厅”；参考网站则是“把作品集融入一个真正可玩的世界”。

核心差距不是有没有 Three.js，也不是单纯模型面数不足，而是：

1. 场景美术与空间组织尚未形成一致的完成度。
2. 玩家角色、镜头和交互对象的视觉主次不够明确。
3. 玩家能移动，但能够影响世界的行为较少。
4. 项目区造型有区别，实际交互仍以统一详情面板为主。
5. 声音反馈、持续探索目标和奖励循环不足。
6. 操控边界、响应式布局和性能验证仍有需要补齐的地方。

**总体路线：先修基础问题，再打磨一个完整的小区域，最后把验证有效的设计扩展到三个项目区。不要先扩地图，也不要继续依靠堆树、水晶、光带和玻璃面板制造“完成感”。**

## 2. 评估依据与范围

### 2.1 参考对象

- [Bruno Simon 当前网站](https://bruno-simon.com/)。本次参考的是当前新版，不仅是早期橙色小车版本。
- [参考网站公开源码](https://github.com/brunosimon/folio-2025)。只用于核实技术与功能事实，不作为复制来源。
- 当前 Ageha 工作区代码，包含评估时尚未提交的修改；不是只依据最近一次提交。
- 浏览器中的场景实图、导航传送、AgehaOS 地标和详情面板体验。

参考站的保龄球、赛道、音频与成就系统等判断结合了公开源码和页面信息，不代表本次逐项完成了全部玩法测试。

### 2.2 验证限制

- 本次没有进行两站同设备、同视口、同画质条件下的性能基准，不能给出具体 FPS 差值。
- 没有完成真实手机、手柄或全部参考站玩法的验证。
- 下文性能数值与体验检查项属于后续验收目标，不是已经达到的结果。
- 历史性能报告只能作排查背景，不能替代当前版本复测。

## 3. 技术与资产使用原则（2026-10-29 修订）

站长已明确取消“不引物理引擎、不引后处理栈、无音效、零外部 3D 资产”的限制：**只要能够完善项目，允许使用合适的引擎、库、工具和资产，不把零依赖或纯程序化当成目标。**

本次修订同步写入 [权威需求简报](3d-world-brief.md) 与 [施工蓝图](3d-world-blueprint.md)，替代其中对应的旧技术禁令。选型以实际体验、视觉质量、兼容性、运行成本和可维护性为依据，不再为这些技术类别重复请求解除限制。

### 3.1 可采用的技术路线

| 方向 | 建议评估的方案 | 使用原则 |
| --- | --- | --- |
| 物理与碰撞 | Rapier、`@react-three/rapier` 等成熟物理方案 | 角色接触、推撞、约束和动态物件均可使用；先做样板，明确物理系统与原控制器的位置更新职责 |
| 后处理 | `@react-three/postprocessing` / `postprocessing`，按需组合 Bloom、环境遮蔽、色彩调整、抗锯齿或景深 | 可以进入正式渲染管线；按画质分级，保证角色与信息可读性，不要求全部效果同时开启 |
| 声音 | Web Audio / Three.js 空间音频，或适合项目需求的音频库 | 正式补充交互、运动、环境与音乐层，支持静音、音量、用户手势启动和资源释放 |
| 外部 3D 资产 | Blender 制作或有明确授权的模型、GLTF/GLB、PBR 纹理、HDR、骨骼动画和烘焙资源 | 可与程序化资产混用；统一风格、尺度、材质和碰撞代理，不机械保留纯几何方案 |
| 资产处理 | 模型简化、LOD、纹理烘焙、Meshopt / Draco / KTX2 等适用工具 | 按资产与设备实测选择压缩方案，同时计算解码开销与依赖成本 |
| 其他必要工具 | 动画、状态管理、性能分析与测试工具 | 有明确收益即可采用；不为依赖数量好看而重复造轮子，也不无目的堆库 |

以上是可选技术路线，不是已经安装或完成兼容性验证的清单；具体版本在实施时核实。现有 Next.js / React 作为起点，不为模仿参考站无目的迁移；其他架构调整如有明确收益也可评估，但不得丢失现有业务能力。

### 3.2 继续保留的品质与业务边界

- 保留冰蓝、蝴蝶、浮岛的原创品牌方向，不复制参考站的场景、素材或具体设计。
- 保留三个真实项目的名称、简介、封面、状态、已有链接与技术栈。
- Moss World 仍为可本地运行的项目，不编造上线地址、源码入口或能力。
- 保留项目列表、详情、关于、技术栈、文章、联系等原有路由以及 SEO。
- 探索不是获取信息的唯一路径，快捷导航和无 WebGL 降级必须保留。
- 新增资产和依赖须核实来源与许可证；运行资源以本地或稳定可控的方式交付，不把“允许使用”理解为可以忽略授权。
- 新技术通过样板区效果、性能和多端测试后再扩展，不把省依赖置于品质之上，也不以品质为由跳过验证。

本轮只更新文档与选型边界，不表示功能已经实现。技术类别已获准；涉及实际付费、订阅、购买资产、对外发布或共享系统变更时，仍须取得对应操作的授权。

## 4. 差距清单

| 维度 | 参考站的表现 | 当前项目的差距 | 优化重点 |
| --- | --- | --- | --- |
| 场景组织 | 道路、河流、植被、建筑、道具互相建立空间关系 | 平台、连接桥、中央装置的构图重复，沿途内容较少 | 做出有用途、有前后关系的区域，而非继续散放装饰 |
| 美术统一性 | 风格化模型与环境细节密度协调 | 蝴蝶较精细，部分地面、植被和建筑相对简化 | 统一轮廓、尺度、细节层级和材质语言 |
| 色彩与光影 | 冷暖、明暗和材质对比帮助识别物体 | 大面积浅蓝、白色接近，角色和路径不够突出 | 保留冰蓝，同时拉开角色、道路、背景的明度和色相 |
| 镜头与主角 | 镜头服务驾驶，主角位置、朝向和动作明确 | 首屏更像远眺景观，大蝴蝶醒目，小信灯容易被忽略 | 区分品牌地标与可操控角色，优先保证操作可读性 |
| 操控与物理 | 行为与碰撞形成连续反馈 | 已有惯性和边界保护，但主要是位置移动与静态推出 | 先修操控，再增加玩家能够影响的物件 |
| 项目交互 | 不同区域提供不同活动 | 三个地标主要都进入同一种详情面板 | 每个项目增加一个简短、独特的场景体验 |
| 探索动力 | 秘密、地图、成就与奖励支撑继续探索 | 已有画廊和蝶舞等彩蛋，但进度较短且缺少持久化 | 用少量有意义的发现串起路线，不做空洞成就墙 |
| 声音反馈 | 音乐、环境和动作声音共同支撑世界感 | 当前没有音效系统 | 优先补交互与运动声音，音乐不是唯一重点 |
| HTML 界面 | 常态尽量把画面让给世界 | 导航、介绍卡和多组工具按钮仍较显眼 | 合并重复入口，渐进显示提示，保留信息可达性 |
| 性能与适配 | 丰富世界依赖持续的渲染与资源管理 | 已有分档和降级，但仍需当前版本的行为与真机验证 | 优化贯穿各阶段，不在最后简单关特效收尾 |

## 5. P0：修复基础操控与布局

### 5.1 碰撞速度方向

证据：[usePlayerController.ts:212](../components/world/systems/usePlayerController.ts#L212)。

当前法线使用“原位置减推出位置”，但速度投影处理条件与该方向不一致，会保留撞向障碍的速度，并可能消掉离开障碍的速度。

行动：统一碰撞法线方向与速度投影条件，保留离开障碍和沿障碍切向移动的分量。

验收：分别测试朝障碍移动、背离障碍、沿侧面滑行、斜向接触和持续顶住障碍；不能只验证最终位置在碰撞体外。

### 5.2 多键与摇杆输入

证据：[usePlayerController.ts:65](../components/world/systems/usePlayerController.ts#L65)、[usePlayerController.ts:141](../components/world/systems/usePlayerController.ts#L141)。

行动：

- 分别记录按键状态，再计算移动轴；建议相反方向同时按下时抵消，松开一侧后恢复另一侧输入。
- 正确处理 WASD 与方向键的同义输入，避免松开其中一个就清空仍被按住的方向。
- 保留摇杆幅度，使微推与满推具有区别；同时限制斜向移动不获得额外速度。
- 检查左右 Shift 同时使用及窗口失焦后的状态清理。

验收：覆盖 W → W+S → 松开 S、W+方向上 → 松开 W、轻推／满推摇杆、斜向移动和切出窗口等实际操作。

### 5.3 低帧率下的运动一致性

证据：[usePlayerController.ts:115](../components/world/systems/usePlayerController.ts#L115)。

当前直接将每帧时间限制为最多 1/30 秒，持续低于 30 FPS 时，运动会相对真实时间变慢。

行动：评估固定步长补步或其他保留经过时间的积分方案；限制恢复后的追帧量，避免切回后台页面时突然大幅位移。

验收：比较不同帧率下等时长输入的移动距离，覆盖前后台切换、边界和碰撞场景；不能通过去掉时间上限而引入穿透。

### 5.4 详情封面被压缩

证据：[globals.css:1221](../app/globals.css#L1221)、[globals.css:1242](../app/globals.css#L1242)。

本次较矮桌面窗口中，AgehaOS 详情封面被挤成细横带。封面位于纵向 Flex 容器中，桌面规则没有禁止收缩。

行动：保护封面比例和尺寸，让详情正文区域承担滚动；保持关闭、返回和项目链接可达。

验收：三个项目逐个检查，覆盖窄桌面、矮桌面、常规桌面、手机横竖屏和文字放大；封面不塌缩，正文和按钮不被截断。

## 6. P1：完成出生区体验样板

### 6.1 范围

只选择“出生点 → 主岛广场 → 一段项目接近路径”作为第一轮样板。不先扩大整个世界。

这个区域需要同时验证角色、镜头、道路、美术、交互和性能，不能只精修一只蝴蝶或一座建筑。

### 6.2 角色与镜头

- 调整小信灯的轮廓、尺度、颜色和贴地表现，避免成为白色地面上的不明确光点。
- 保留大蝴蝶作为品牌地标，但不要让初访者误以为它就是可操控角色。
- 分别校准初始、移动、接近地标、转身和返回起点时的构图。
- 用克制的倾斜、光翼变化和尾迹强化速度与方向感，不通过强烈晃动制造“手感”。
- 所有镜头调优同时检查角色可见性、地标遮挡、道路辨识和触屏操作。

### 6.3 场景与美术

- 为前景、中景、远景设定职责：前景建立尺度，中景承载操作，远景营造纵深。
- 通过路面、路肩、转折、桥头与地标入口建立连续路线，减少“平台之间细线相连”的感觉。
- 让树、岩石、灯具、池岸和建筑形成有意图的组合；每组物件服务于指路、框景或区域识别。
- 保留冰蓝基调，通过深色结构、局部暖色与自然材质区分重点；不把所有对象做成透明玻璃。
- 统一蝴蝶、地形、植被和建筑的细节密度；可使用 Blender、外部模型、PBR 纹理和烘焙资源替换表现不足的程序化物件。
- 将光照、材质、接触阴影、色彩调整和适当后处理作为完整画面共同设计；在样板区比较环境遮蔽、克制的 Bloom、抗锯齿及可选景深，不靠增加特效掩盖构图问题。
- 先在样板验证新资产的尺度、授权、加载与解码开销，再扩展到其他区域。

### 6.4 界面减负

- 常态只保留简洁品牌、必要工具入口及当前交互提示。
- 合并重复项目入口，保留快速查看项目、关于、联系和返回起点的能力。
- 首次提示简短、可关闭，键位在需要时再展开；不要求读完一大块说明才能开始。
- 保留清晰的键盘焦点、关闭方式与减少动态模式。

### 6.5 样板验收

- 初访者无需解释，能够快速指出自己控制的角色，并找到一条可以前进的路线。
- 出生、移动、接近地标、转身四类画面中，角色和交互对象均清晰可辨。
- 样板至少包含一种由玩家触发、结果明确且可重复体验的互动。
- 项目入口不被装饰、导航或提示遮挡；跳过探索仍可访问全部项目信息。
- 保存固定位置和固定 CSS 视口的前后对比图，同时验证移动过程，不能只挑一个最佳截图角度。

## 7. P2：建立玩家与世界的反馈闭环

### 7.1 先做一种好玩的机制

候选机制包括推动一组轻质浮晶、点亮路径节点、触发桥头装置或与引导蝶完成短互动。第一轮只选一种，避免同时引入多套玩法。

每种机制必须形成完整闭环：

**看得懂的对象 → 明确操作 → 世界状态变化 → 动画／视觉／声音反馈 → 能够重试或继续探索。**

- 仅有悬停变色、自动旋转、靠近弹文字，不算完整的玩法闭环。
- 对角色接触、物件推撞与约束，直接评估成熟物理引擎；不为了保留自写运动学而降低交互品质。简单开关与装饰动画不必强行使用刚体。
- 接入物理系统时同步规划步进、碰撞代理、休眠、复位和角色控制职责，避免与原有位置更新互相冲突。
- 交互物不得堵死主路径，必须有明确复位方式；低性能模式仍能完成同一交互。

### 7.2 补声音层

优先顺序：交互确认／取消 → 移动或接触反馈 → 区域环境声 → 背景音乐。

- 根据速度、动作或距离改变声音，避免所有反馈都是同一个提示音。
- 用户手势后才启动音频，提供清楚的静音与音量控制。
- 控制同时播放数量，页面隐藏时暂停不必要播放，并正确释放资源。
- 静音时全部功能仍可完成，重要结果不能只通过声音传达。
- 资源授权未确认前，不引入外链音频、不下载参考站声音作为项目资产。

## 8. P3：让三个项目区提供不同体验

在保留真实项目详情入口的前提下，每区增加一个简短、可退出的场景互动。下列是候选方向，不是已实现功能或对项目能力的新宣称。

| 区域 | 候选体验 | 必须守住的边界 |
| --- | --- | --- |
| AgehaOS | 在场景终端中切换窗口或唤醒少量应用图标，展示系统式交互概念 | 明确是作品集内的演示，不重做完整 Web OS，也不冒充实时连接项目 |
| CS 模拟器 | 操作一个简化观测装置，切换不同展示视图 | 如使用演示数据必须明确标注，不伪装实时行情，不新增未经证实的投资功能 |
| Moss World | 调节演示舱的光照或雾感，让视觉环境发生变化 | 明确是场景演示，不宣称完整生态模拟；继续保留“可本地运行、无公开入口”的真实状态 |

同时改变空间组织，而不只是更换中央雕塑：终端区强调工作台与屏幕，观测区强调仪表与观察路线，生态区强调近距离观察与植物层次。

验收：

- 不读名称，也能通过轮廓、材质和环境区别三个区域。
- 每区至少有一种与其他区域不同的操作结果。
- 体验后可以进入真实详情，也可以立即退出；不能用小游戏阻挡项目访问。
- 三个项目的名称、封面、状态和已有链接继续来自现有数据源。

## 9. P4：少量探索目标与进度

在核心机制成立后再添加探索奖励，不先做大规模成就系统。

- 围绕现有画廊、引导蝶和三个项目区设计少量发现目标。
- 让路线上的支点包含可观察或可操作内容，减少没有变化的长距离移动。
- 已发现区域、已完成的小互动可保存在本地，并提供重置入口；不为此新增账号系统。
- 状态保存失败不能影响正常访问；不保存不必要的个人信息。
- 奖励优先使用局部景观变化、新的观察角度或小型视觉变化，而不是只有一个计数加一。
- 任何收集或解锁均不得锁住项目正文、联系入口和原有路由。

验收：发现结果明确，刷新后按设计保留；复访和首次访问都能理解当前状态；进度重置后不出现残留或无法再触发的对象。

## 10. 性能、加载与多端验证：贯穿全程

### 10.1 保留现有基础

继续保留动态加载、画质分档、WebGL 降级、上下文丢失提示、页面隐藏暂停、减少动态模式以及项目快捷导航。

不要为了增加玩法或表现效果，牺牲这些已经建立的可用性能力。

### 10.2 优化方向

- 实测 draw call、三角形、材质、透明物体、阴影、纹理及逐帧 JS 成本，再决定优化对象。
- 重复资产继续实例化或合并；远处区域按需要进行细节或更新频率控制，不无条件每帧更新所有内容。
- 降级优先减少装饰、阴影、透明效果和远景细节，不能让项目内容消失或把可交互展品变成无法理解的空框。
- 音频和项目附加体验按需加载，不把全部新资源塞入首屏。
- 物理、后处理及新渲染技术均可使用，依据其解决的体验或性能问题选型；没有明确收益时不做技术迁移，不以减少依赖为由牺牲效果。

### 10.3 验证矩阵

| 类别 | 必测内容 |
| --- | --- |
| 桌面视口 | 1440×900、1920×1080、2560×1440；补一个较矮桌面窗口 |
| 移动视口 | 窄屏竖屏、横屏、摇杆与观察同时操作、详情滚动、安全区 |
| 真实设备 | 桌面正常档及受限条件；至少一台真实手机，无法获取时明确记录未验证 |
| 主流程 | 进入、移动、碰撞、观察、缩放、传送、三个项目详情、关闭返回、直接访问项目 |
| 边界状态 | 相反方向按键、窗口失焦、后台恢复、边缘滑行、连续复位、快速开关面板 |
| 降级状态 | 低画质、WebGL 不可用、资源加载失败、上下文丢失、减少动态、静音 |
| 性能稳定性 | 初次加载、首次交互抖动、持续漫游、反复切换路由、内存和资源释放 |

性能目标：常见桌面设备争取稳定 60 FPS，低性能设备与手机优先稳定可操作，争取 30 FPS。必须记录设备、浏览器、CSS 视口、DPR、画质档位、构建模式、帧时间和测试路径；不能把目标写成已达到的结论。

自动化测试应覆盖输入状态、碰撞速度和进度行为，不能只检查源码中是否出现某个关键字。构建、类型检查和测试通过之后，仍须真实浏览器操作。

## 11. 实施顺序与阶段门槛

| 阶段 | 主要交付 | 进入下一阶段的条件 |
| --- | --- | --- |
| P0 基础修复 | 控制器、碰撞、低帧率运动和详情布局修复及行为测试 | 基础操作没有已知阻断问题，三个详情入口闭环通过 |
| P1 出生区样板 | 角色、镜头、美术、界面与一个小互动共同完成，可使用外部资产和后处理 | 固定视角与移动过程均通过检查，画质改善没有不可接受的性能回退 |
| P2 世界反馈 | 适用的物理交互、一种可重复互动与完整声音反馈 | 操作、反馈、复位、静音和低画质行为完整 |
| P3 项目区差异化 | 三个区域各自的简短体验与不同空间组织 | 真实项目信息与快捷入口完整，三个体验有明确差异 |
| P4 探索进度 | 少量发现目标、本地进度和复访反馈 | 首访、复访、刷新和重置均可理解且可操作 |
| 全程与最终回归 | 性能、无障碍、多端、加载失败及路由回归 | 未通过项已修复，无法验证项如实列出，不用静态测试替代浏览器验收 |

每阶段保留统一条件的前后对比证据。新增依赖、资产和高级效果的类别已获准，具体方案按效果与成本选择，逐步接入并同步测试，不需要重复申请解除旧禁令。

## 12. 暂不优先做的事项

- 扩建更多岛屿、堆放更多没有用途的装饰物。
- 为模仿参考站而更换成汽车或复制其地图、交互布局。
- 未完成基础美术就叠加大量 Bloom、透明材质、实时反射和灯光。
- 多人联机、排行榜、账号体系、复杂天气、完整昼夜循环和大量小游戏。
- 在作品集中重做 AgehaOS、CS 模拟器或 Moss World 的全部业务。
- 因参考站使用不同渲染技术而迁移整站框架。
- 编写大量只证明“组件存在”的测试，却不验证真实操作。

## 13. 最终验收判断

最终不以“增加了多少模型或功能”判断成功，而以以下问题判断：

- 用户能否立刻知道自己在控制什么、能去哪里、可以做什么？
- 世界是否会对操作产生明确、连贯、令人愿意再次尝试的反馈？
- 冰蓝、蝴蝶、建筑、地形和界面是否属于同一个完整美术体系？
- 三个项目是否拥有各自的空间记忆点和体验，而不只是三个详情按钮？
- 不愿探索或设备不支持 3D 的用户，是否仍能顺畅获得全部信息？
- 品质改善是否经过真实浏览器和明确设备条件下的验证？

**目标不是复刻 Bruno 的内容体量，而是先让 Ageha 的一个小世界，在视觉、操控、反馈和信息访问上达到同样认真打磨的程度。**
